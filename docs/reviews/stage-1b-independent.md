# Independent code review - Stage 1b (interactive slice)

Reviewer: an independent read-only session with fresh context (started 2026-11-04, paused once for a usage limit, finished 2026-11-04). It did not take `STATUS.md`, `CONTEXT.md`, the hand-over notes, the test counts or the other review file `docs/reviews/stage-1b.md` (commit `cf63d2b`) on trust; every finding below was re-derived from the code and, where it is about behaviour, reproduced with an experiment on the current `main`. Scope: everything new in Stage 1b (`Core/Hotkeys`, `Core/Reports`, `Platform/Hotkeys`, `Frames/Incidents`, `Frames/Capture`, `Jankscope.App`) and their tests, ADR 0008 and the Stage 1b test plan.

**Working method.** The real repository was only read (its `git status` was clean before and after). All experiments ran in private copies outside the repo: `PC FPS booster - review1b` (the tree of the first commit `d0b3e7f`, reviewed first), `PC FPS booster - review1b-main` (current `main`, `f00ac09`, experiments and the live run) and `PC FPS booster - review1b-mut` (clean copy for the mutation campaign; every mutated file was restored and the copy diffed against the repo afterwards). No network, no install, no download, no commit. The live run started the real `jankscope-app.exe` and the real harness window with the repo's pinned PresentMon; every process and ETW session it started was checked afterwards (`logman query -ets` shows no `Jankscope-*` session left). The review was first done on `d0b3e7f`; the authors' fixes in `cf63d2b` and later were then re-checked one by one, so a finding that is already fixed is listed under "Fixed on main".

**Baseline (private copy of current main, `build.ps1 -Clean`):** 0 warnings, 0 errors; banned-symbol proof 106 entries / 109 proof lines / 11 controls clean; analyzer wiring proven for 7 product projects; smoke "41 capability rows, 14 probes, 0 failed". Tests: Core 767 + Frames 1,099 (1,097 passed, **1 failed**, 1 skipped) + Harness 266 + Platform 344 + App 32 = **2,508**. The failing test was `RunnerRealBinaryTests.A_live_capture_against_the_visible_harness_detects_injected_hitches` ("expected rows, got 0"); alone it passed once and failed once, so it is flaky on the bench (the first snapshot copy had a different flaky Stage 1a test, `RunnerSupervisionTests.Stop_when_the_helper_hangs_...`, 1 failure in a full run, 3 of 3 passes alone). `build.ps1` stops at a failed test step, so a fully green `build.ps1` was not obtained here. The owner's CI screenshot shows the GitHub Actions run failing in the same step (exit code 1, test not identified).

Severity legend (as in the earlier reviews): **High** = a hard constraint's guarantee is false or fails open under realistic input, silently. **Medium** = a safety property is unguarded, a guard has a confirmed bypass, or a documented claim is wrong, with no present harm. **Low** = hardening, wording, test hygiene.

## Experiments and evidence

### Live run of the real application (current main)
Script `live-run.ps1`, UI Automation plus a test-only key sender; the real harness (144 fps, 30 hitches of +60 ms, `--window-visible`) was the program watched.
- Capture starts: child `PresentMon-2.6.0-x64.exe` of the app, ETW session `Jankscope-<pid>-live-1`, status "Capturing jankscope-harness.exe".
- **Ctrl+Alt+F9 -> "Marked a stutter. Open the investigator to choose where it happened."**; the investigator offered "Frame 966: 67.1 ms, 60.1 ms longer than the 7.0 ms median (Severe), 2.4 s before the key press" and "Frame 542 ... 5.4 s before"; the selection status read "No event time was chosen. The moment the key was pressed was not used as the event time." (nothing aligned to the key press).
- A second copy of the program exits within 5 s and leaves one process. Closing the window only hides it: the process and the PresentMon child keep running.
- Hidden and capturing: **0.15 % of total CPU capacity** (16 logical processors; about 2.4 % of one logical processor), working set **206 MB idle, 231 MB capturing**, 24 to 34 threads. **0 TCP connections and 0 UDP endpoints** for the app and for the PresentMon child.
- Forced kill of the app (a crash): the PresentMon child (orphan, parent gone) and the ETW session were still there 8 s later; starting the app again removed both within 25 s (the start-up orphan cleaner works; the orphan lives until then).
- Tray "Quit" could not be driven (the Windows 11 notification area is not reachable through UI Automation here). The Quit path was run instead as the same code, `AppHost.DisposeAsync`, against the real PresentMon and harness (A3): 94 ms, no PresentMon child, no ETW session, second dispose safe.
- A real export of this PC (41 real capability rows through `PrepareExport`, A2) contained **none** of this machine's identifiers, even unredacted: user, PC name, domain, six IPv4, six IPv6 addresses, two MACs, BIOS and board serial, disk serials, product UUID, SSID and BSSID were all absent. The only way a personal value reaches a file today is therefore the free-text note and the program name.

### Frame and time model (E-series, `ReviewProbes1b.cs`)
E1/E6/E2C: see "Fixed on main". E2A: one observation (delivery 300 ms) gives uncertainty 0.0. E2B: 100 ms batches plus 40 ms latency: a key press at real 20,000 ms is mapped to 19,960 ms with uncertainty 92 ms (band 19,868 to 20,052), so the unmeasured 40 ms floor sits outside the band's centre; with 150 ms latency the true time falls outside the band. E3: 144 fps chain plus a 1 fps chain of one process: all five offered candidates are the 1 fps chain's 1,000 ms rows (severity 993 ms). E4: 6 s, 1 writer, 2 snapshot readers, 1 copy reader, 3 recorder threads, 53 M writes, 85,721 reads, 5,382 marks: 0 torn or misordered, 0 unexpected exceptions. E5: the live refresh costs 0.37 / 0.81 / 2.16 ms and 50 / 145 / 339 KiB per call at 60 / 144 / 360 fps (four calls a second = 0.15 / 0.32 / 0.86 % of one core). E7: 1,000 rows of which 50 are stamped 8 ms earlier than the row before: 50 are dropped and counted as "ignored". E8: one row stamped +30 s followed by 5,000 normal rows: 779 received, 4,322 ignored.

### Redaction with this PC's own context (R-series, `ReviewRedaction1b.cs`)
The real values of this PC are deliberately not printed in this file (it is in a public repository); every name, address and serial below is a stand-in of exactly the same shape. Context from `RedactionContext.ForThisMachine()`: a user name and a PC name that are each 5 characters (here `maria` and `MARIA`), below `SubstringMinLength` 6, so whole-word only. Through `ExportPipeline.Prepare` (redactor and guard together), written to the file unchanged: `maria225`, `MariaPC`, `mymaria`, `mariasmith`, `MARIA1`, `maria0`, `0maria`, `mariaX`; a two-character CJK name glued to other CJK text (no word boundaries exist in CJK); an NFD spelling of an NFC name (`Jose` + combining acute); `ip=192.0.2.5_x`, `x192.0.2.5`, `0192.0.2.5`; MACs without a separator (`A1B2C3D4E5F6`, `a1b2.c3d4.e5f6`, spaces); the SSID `Home_Maria Net` (only the word `Maria` is replaced) and the board serial `AB12CD34` (never in the context). Replaced or blocked correctly: names in every path form tried (`C:\Users`, `/`, NT device paths, `file:///`, `\\?\`, 8.3 names), UNC hosts, URLs with a host, e-mail addresses, IPv4 with port or in a URL, IPv4-mapped and zone IPv6, MACs with `:` or `-`. `%74ejas` is blocked (fail closed, with the dialog text "This is a bug in the redaction"); `%2574ejas` passes harmlessly (no name in it). A user named `mark` renames the schema key `mark` to `<USER>` in the export. No catastrophic backtracking: 1 MB of digits or of `a:` is prepared in 120 to 155 ms; `\\` and `C:\Users\` floods are blocked in 1 to 2 ms.

### Static scan of the compiled assemblies (IL, `ilscan`)
`jankscope-app.dll`, `Jankscope.Core.dll`, `Jankscope.Frames.dll`, `Jankscope.Platform.dll` (first snapshot; the changed files add no new references): no `System.Net`, no `Process` or `ProcessStartInfo` in the app or Core (Frames only in the launcher; Platform only `GetProcesses`/`ProcessName`/`Id`), no `Activator`, `Assembly.Load`, `AssemblyLoadContext` or reflection invoke, no pipes. **The app has no P/Invoke of its own.** The only keyboard-related import in the product is `user32!RegisterHotKey`/`UnregisterHotKey`. **Rules whose mutation survived (test gaps; each needs a test that fails when the rule is broken):**

- **H5** (function keys only F1-F24): F25 is accepted as a function key (VK 0x88 is not a function key). No boundary test. Low risk.
- **H6** (only A-Z and 0-9 as plain keys): Punctuation keys (`!` to `/`) are accepted as chord keys. No negative test for a non-letter, non-digit key. Low risk.
- **P1** (MOD_NOREPEAT (holding is one press)): `MOD_NOREPEAT` can be dropped and every test still passes: no test pins the flag handed to `RegisterHotKey`. A held chord would then repeat; the 1 s debounce hides it. Test gap.
- **R8** (known values >= 6 characters match as substrings): Raising `SubstringMinLength` to 100 (every name whole-word only) passes everything: no test glues a 6+ character name to other letters. Test gap (and see finding 2 for the 5-character case).
- **R11** (longest known value first): Shortest-first ordering passes: no test where a host name contains the user name. Test gap.
- **X7** (context knows the profile folder name): Dropping the profile-folder name from `ForThisMachine` passes: no test has a profile folder that differs from the user name. Test gap.
- **F1** (look back 10 s only): A spike 10 to 12 s before the mark (inside the context margin) would be offered; no test sits in that margin. Test gap.
- **F2** (weak spike offered after real candidates): Weak spikes are not forced after real candidates by anything but their usually lower severity; no test builds a weak spike with larger severity than a real event. Test gap.
- **F5** (stutter events outside the window are not offered): The explicit filter of stutter events to the window passes: the context margin is the only other limit and is not tested at its edge. Test gap (same area as F1).
- **F7** (unknown clock gives no candidates): Removing the non-finite check on the mark time passes. It is a defensive check (the clock map never produces a non-finite time), so near-equivalent; the real unknown-clock rule (a null mark time) is killed by its own test.
- **Q6** (pre-roll covers the clock uncertainty): The pre-roll window ignoring the clock uncertainty passes: no test makes the uncertainty large enough to change which frames fall inside the pre-roll. Test gap (finding 3 is the related honesty point).
- **S2** (weakest provenance wins (ContinueWith)): When the post-roll is appended to the frozen pre-roll, the weakest provenance of the two is not tested: a Simulated or Fixture post-roll after a Measured pre-roll would be labelled Measured. Test gap (HC-9).
- **C2** (a new capture run resets the clock): Near-equivalent: the 5 ms backward-step rule in `CaptureClockMap` already starts a new epoch when the new run restarts at zero; the explicit reset per run matters only when the restart lands within 5 ms of the old newest stamp, and no test covers that. Test gap (low).
- **L2** (a new capture starts a fresh clock): The controller resetting the clock before a new capture passes: for the same reason as C2 the 5 ms rule hides it, and no test starts a second capture whose clock continues from the first. Test gap (low).
- **L5** (only WM_HOTKEY is acted on): `HotkeyHost.OnMessage` acting on any message whose wParam equals a registered id (the WM_HOTKEY check removed) passes: no test sends another message with that wParam to the window. Test gap (HC-4: the handler should react to WM_HOTKEY and nothing else).
- **L6** (the live capture is Measured only for PresentMon output (factory)): The live capture factory labelling its frames `Simulated` instead of `Measured` passes: no test touches the factory (and so none can notice that the harness is labelled `Measured`, finding 6). Test gap.
- **P-HC4** (PLANT: managed key-reading handler (HC-4 lint should refuse it)): PLANT, not a rule: a `PreviewKeyDown` override in `MainWindow` that stores every `Key` passes all 767 Core tests (including every repo lint) and all 32 App tests. This is finding 5 (HC-4 unguarded for managed key-reading code).
- **B8** (clock uncertainty stated in the export): Raising the threshold of the export note about clock uncertainty (20 ms) to a huge value passes: no test checks that a large uncertainty is stated in the export. Test gap (related to finding 3).
- X4 (no overwrite by default): Equivalent mutant: `File.Move(..., overwrite: false)` refuses an existing file by itself; the explicit pre-check only gives a nicer message. Not counted.

## What I verified is correct
- **HC-4 as built.** No code path reads a key code outside the focused timeline; the hotkey handler reads the registration id only; no per-key timestamp exists anywhere (IL scan and reading); `HotkeyChord` refuses chords without Ctrl or Alt, with the Windows key, Alt+F4 and Ctrl+Alt+letter (mutations H1 to H4 killed).
- **HC-1 and HC-5.** Static: see the IL scan. Dynamic: 0 TCP and 0 UDP for the app and its PresentMon child while capturing. No overlay window flags, no `Topmost`, no web view, no link, no update check in the app project.
- **Export.** `ExportPipeline.WriteAtomic` is the only export writer (the app's other file writes are the settings file and `error.log`); it writes `preview.Bytes` and nothing else (mutation X3 killed); `Prepare` runs the guard unless the person switches redaction off in the dialog (clearly warned); the guard fails closed and never prints the value.
- **Honesty.** A mark has no anchor until the person chooses (Q1, Q2 killed; live run); the pre-roll is never padded and a short one is stated; an unknown clock gives no candidates; a candidate that is only a weak spike is labelled; unusable frame times are skipped, not zeroed; non-measured provenance is labelled in the export.
- **Time model.** Epochs, restarts and run changes are now handled; concurrent observing and estimating is consistent (E4).
- **WPF app.** One instance, tray residency, hotkey end to end, no sockets, clean Quit path, orphan cleanup after a crash at next start.
