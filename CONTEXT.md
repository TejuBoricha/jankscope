## 1. What this is
**Jankscope**: a free, open-source (MIT), no-telemetry Windows tool that explains *why* a game stutters, a wireless mouse freezes or online play lags, using evidence-graded hypotheses. It changes a setting only when it can prove the benefit and undo it. It is not a "booster".

## 6. How the code is guarded (do not fight these; read the failure)
- **Banned-API analyzer** (RS0030, an error): `BannedSymbols.txt` bans the whole `Process` type (one pragma exception for the name-only snapshot in `ServiceState.cs`, one for the runner's `PresentMonProcessLauncher.cs`), network types, registry writes, reflection and dynamic loading, COM interop, WMI methods, remote targets. A **method** entry needs the exact overload signature or it silently bans nothing; every entry needs a proof line in `tools/dev/analyzer-coverage/Coverage.cs.txt`. `DllImportAttribute` cannot be symbol-banned (the LibraryImport generator emits it).
- **Text lints** (`RepoLintTests`, `ProductLints`, `CSharpScanner`): native names, process members, vendor words (`catalogs/vendor_terms.json`), exact set of native imports (`ApprovedLibraryImports`, only `[LibraryImport("lit.dll", EntryPoint = "Lit")]`), System32-only DLL search, ASCII-only code, no `unsafe` outside `Jankscope.Platform`, one `Directory.Build.*` of each kind, product projects only under `src/` or `tools/`, packages versioned only in `Directory.Packages.props` with a matching `docs/THIRD_PARTY.md` row.
- **Optimize-mode gate** (HC-11): every input row must emit an exact value from `ManagedValues` or it blocks; `anticheat.state` is Unknown until a game-session detector exists. `mode.optimize` is therefore Recommend-only today (intended).
- **Build proofs**: `tools/dev/verify-banned-symbols.ps1`, `verify-analyzer-wiring.ps1`, `test-smoke-gate.ps1` are part of `build.ps1`.
- Exceptions need a written reason, an entry in `RepoLintTests` (`Allowed`, `BannedApiExceptions`, `ApprovedLibraryImports`) and independent review.

## 7. Pitfalls learned the hard way
- **Encoding:** Windows PowerShell 5.1 `Get-Content`/`Set-Content` corrupts UTF-8. The file-writing tools turn backslash-u escape sequences into literal characters: write `(char)0x...` or build the text from parts. A lint rejects mojibake and invalid UTF-8.
- **Shell quirks:** Git Bash heredocs can mangle backslashes and quotes (write a script file with the file tool and run it with Node); Node run from Git Bash cannot see bash's `/tmp`; the shell's working directory drifts after `cd` (always use absolute paths); `Jankscope.slnx` has CRLF line endings; `patch` fails on CRLF.
- **The file tools need a fresh Read** after a file changed on disk; "file changed" notices are usually your own earlier script.
- **Mutation experiments** (break a rule, see a test fail, restore) belong in a scratch copy of the repo, never in the live tree while another session reads it. Compile errors from "unreachable code" invalidate a mutation: use runtime-false conditions.
- **A loaded PC makes timing tests fail (probable cause of the two live-capture failures below, not proven):** on 2026-11-12 other programs (a Razer service, two `Antigravity` processes, VS Code) held the CPU, and the Core tests took 46 s instead of 1 to 3 s. Look at `Get-Process | Sort-Object CPU -Descending` before blaming a change, and re-run when the machine is quiet. Timing assertions in new tests must be generous and must read state in a safe order (see `SimulatedFrameSourceTests`).
- **Live capture tests depend on the desktop:** `RunnerRealBinaryTests.A_live_capture_against_the_visible_harness_detects_injected_hitches` and `AppHostTests.Real_presentmon_and_visible_harness_end_to_end_mark_anchor_and_redacted_export` capture a real visible D3D window through PresentMon. On 2026-11-12 they passed in one local gate and then failed 3 of 3 on the *same* commit later the same day, with the session unlocked (cause not found; a `PresentMonService` process was running, and the display state could not be checked). They skip on CI (no interactive desktop). Later the same day a full gate ran them and both live-capture tests failed ("no frame rows arrived (lines read: 0)", "Timed out waiting for: frame rows from the real executable") with the Frames code identical to the green `main`; every run after that skipped them ("no frames were presented on this machine during the probe (no display session?)"), so the display state of this PC flips between runs. No leftover `Jankscope-*` ETW session existed; a `PresentMonService.exe` was running. Cause still not found. Before blaming a change, re-run them on the last green commit (`git checkout --detach <sha>`, rebuild, run the two tests); do not skip or loosen them. On 2026-11-13 the App one failed ("the condition was not met in time", `AppLogicTests.cs:527`, waiting for 150 frames) in the main checkout on the unchanged green commit `e008ff5` and on a change that does not touch capture, then passed in a full gate in a clean worktree and in a standalone re-run, with no code change; a `qemu-system-x86_64` and a Razer `rzappengine` process were holding the CPU.
- **A checkout nested inside the repo used to break the local gate** (fixed in #38: a directory with its own `.git` entry is skipped by `Repo.AllFiles`, `verify-analyzer-wiring.ps1` and `build.ps1 -Clean`; the rest of this note still applies to any other tool that walks the tree): Claude Code's `EnterWorktree` creates linked worktrees under `.claude\worktrees\`, which is inside the repo root. `build.ps1` then failed at "Verify analyzer wiring" (it walked into the copy's unrestored projects) and the lints scan everything under the root. Do not delete such a worktree: it may hold commits that exist nowhere else (the one found on 2026-11-13 held a commit that was on no remote at the time; the same subject was merged a little later as #36, which was not checked further). To gate a change meanwhile: commit it, `git worktree add C:\tmp\jgate HEAD --detach`, copy `third_party\PresentMon` in (git-ignored), run `build.ps1` there, then remove the worktree (a leftover build-server process can hold files, so the removal may need a retry).
- **A force-push is blocked by the permission classifier** here, even `--force-with-lease` on your own PR branch. When a PR branch falls behind `main`, merge `main` into the branch and push normally; the squash-merge flattens it. Branch protection needs the branch up to date, and another session merging meanwhile makes that happen (it did for #37).
- **Fake-clock tests must wait for the timer they advance past, not "a timer"** (`ManualTimeProvider`): the runner's 10 s watchdog is armed for the whole run, so `PendingTimers >= 1` is already true while the grace or cleanup timer does not exist yet; advancing first skips it and the stop hangs. Fixed in #34 for the two stop tests (proven by a real delay in the runner); other uses of `PendingTimers` / `AdvanceWhenArmed` were not audited.
- **`D3dHarnessTests.A_hardware_run_follows_the_schedule_within_tolerance` is a known flake, on CI and locally** (not caused by the change under test): on 2026-11-13 it failed on PR #41's CI run 43295904498 (`p99 Present() error 16.884 ms > 16 ms`; the CI runner's adapter is the software 'Microsoft Basic Render Driver', whose test limit is 16 ms, only 0.4 ms above the 15.6 ms timer quantum; the same run's max was 24.8 ms) and passed when only the failed job was re-run (`gh run rerun <id> --failed`); it also failed once in a local gate on this PC with a `qemu` process using the CPU and passed twice alone. The test file says 'a hard cap would make this suite fail about once in fifty runs'; it is more often than that on a loaded runner. Do not loosen it silently: a principled fix (for example a limit of two timer quanta for the software adapter, or only the disturbed-frame budget there) is a decision for the owner.
- **Timing tests** (frame pacing, sampler drift, watchdogs, ring stress) need the test projects to run one at a time; probes in `CapabilityMatrixBuilder` use `TaskCreationOptions.LongRunning` so a hung probe never starves the `.NET ThreadPool` on 2-vCPU CI runners.
- **WPF and the banned-API rule:** WPF generates a reflection helper (`GeneratedInternalTypeHelper.g.cs`, uses `Activator`) whenever XAML needs run-time wiring: an event handler inside a template, or a reference to a type of the same assembly. RS0030 rejects it, and no suppression route is allowed. So: no `Click=` inside a DataTemplate (attach one handler to the list in code) and create `TimelineView` in code, not in XAML.
- **A window test must not assume a big screen:** the operating system will not make a window larger than the screen, so `window.Width = 1700` is only as wide as the machine allows, and a CI runner's screen is small (this PC's is 1920 by 1080). A test that expects "a roomy window is not scaled" passed here and failed on CI (PR #35, first run). Assert the rule against the viewport the window actually got (`AssertScaledAsTheRuleSays` in `WpfTests`), and prove such a test with `window.MaxWidth`/`MaxHeight` set small, which is what a small screen does.
- **Rendering check:** `JANKSCOPE_SNAPSHOT_DIR=<dir> dotnet test tests/Jankscope.App.Tests` writes PNG renders of every window and the timeline; look at them after any UI change.
- **Exports:** the guard checks decoded JSON strings, because a JSON-escaped path (`C:\\Users\\...`) is not the path as text. Known short user names (under 6 characters) match as whole words only (documented in `Redactor`).
